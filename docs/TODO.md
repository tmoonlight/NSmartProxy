## HTTPS 阻塞问题（已修复记录）

挂证书之后请求经常卡住，是下面几个问题叠加造成的：

1. `ReadHostName` 用 `PipeReader.Create(stream)` 读请求头，该重载默认 `leaveOpen = false`，
   `CompleteAsync()` 会把底层流 Dispose 掉。结果是 Host 刚解析完、隧道还没开始转发，
   消费端的 `SslStream` 就已经被关闭了。已改为 `StreamPipeReaderOptions(leaveOpen: true)`。
2. TLS 握手用的是同步的 `AuthenticateAsServer`，会占住线程池线程；线程池扩容很慢，
   并发一上来就会饥饿，连带侦听循环和其他隧道一起卡死。已改为 `AuthenticateAsServerAsync`。
3. 握手没有超时，底层 `NetworkStream` 默认永不超时，
   连上来不发 ClientHello 的连接（扫描器、误发的明文 HTTP）会永久占住资源。已加握手超时。
4. `checkCertificateRevocation` 为 `true`，会引入可能长时间阻塞的 CRL/OCSP 网络请求；
   服务端并不校验客户端证书，已关闭。同时协议放开为由系统协商（支持 TLS 1.3，少一个握手往返）。
5. 证书用 `X509Certificate2.CreateFromCertFile` 加载，不支持带密码的 pfx，
   上传只含公钥的 cer/crt 也不报错，于是每个连接都在握手时抛异常、连接一直挂到超时。
   已改为加载时即校验私钥并给出明确错误。
6. `PortCertMap` 是普通 `Dictionary`，被 Web 管理接口写入的同时被每个连接读取，
   并发读写可能损坏内部结构导致查找死循环（CPU 100% 且请求全部卡住）。已改为 `ConcurrentDictionary`。
7. 握手失败、未解析出 Host 等分支没有关闭消费端连接，socket 持续泄漏。已统一回收。

## HTTP 阻塞问题（已修复记录）

HTTP（不挂证书）同样是坏的，而且和证书无关，原因是另外几个：

1. 上面第 1 条的 `PipeReader` 问题对明文 HTTP 一样生效。
2. 控制帧被读多了。服务端发完 5 字节的 TCPTransfer 控制消息后，会紧接着把
   之前为解析 Host 而消费掉的 HTTP 头写进同一条连接，两次写入会被 TCP 合并成
   一个报文；而客户端 `OpenTransmission` 一次性读 10 字节，把业务数据的前几个
   字节一起吞掉后丢弃。首个请求因此丢掉开头 5 个字节（`GET /` 被吃掉，后端收到
   `" HTTP/1.1"` 直接 400，或者一直等不到完整请求行而挂住）。是否触发取决于 TCP
   是否合并报文，所以表现为时好时坏。已改为按帧精确读取。
3. `Host` 头里带端口（浏览器访问非 80/443 端口时必然带），而客户端注册进来的
   host 是不带端口的，导致多 host 共用一个端口时永远匹配不上，静默回退到
   `ActivateApp`，请求被转发到错误的后端。已改为先精确匹配、再去掉端口重试。
4. 未匹配到 host 时直接 `nspAppGroup[host]` 取值会抛 `KeyNotFoundException`，
   而此时已经从池里弹出的反弹连接不会被关闭；反复用未知 Host 访问会把客户端的
   反弹连接池抽干。已改为与 `GetClientForTcp` 一致的回退逻辑。
5. 隧道拆除过早。服务端和客户端都是 `Task.WhenAny` 一返回就把两端 socket 关掉，
   而且两个方向的 pump 各自 `using (fromStream)`，先结束的一方会把另一方还在用的
   流 Dispose 掉。请求方向先结束是常态（浏览器发完请求就不再发数据），于是响应
   经常被拦腰截断，并发越高越明显。已改为共用流统一收尾，并给回程方向留排空时间。

实测（本地 server+client+两个后端，两个 host 共用 20001 端口）：

| | 串行 60 次 | 突发 40 并发 |
|---|---|---|
| 修复前 HTTP | 0/60 | 0/40 |
| 修复后 HTTP | 60/60 | 32/40 |
| 修复后 HTTPS | 60/60 | 33~39/40 |
